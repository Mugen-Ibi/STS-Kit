# 性能と再現方法

2026-09-27、Windows / Ryzen 7 260 / RTX 5070 Laptop 8GB。Gemma 4 E2B it Q4_0 + mmproj Q8_0、llama.cpp b10964、PyTorch 2.8.0 CUDA 12.8、Style-Bert-VITS2 2.5.0 JVNV F1 JP-Extra。

## 改善前後の実測

`scripts/benchmark.py --rounds 7`で、各条件1回の準備運転の後に7回測定しました。**送信開始から、最初のWAVがWebSocketクライアントへ届くまで**の値です。録音時間・無音待ち・ブラウザ再生・スピーカーの遅延は含みません。会話は同じ質問・同じ世界設定ですが、サンプリングにより返答文や長さは異なります。

|条件|改善前・中央値|改善後・中央値|短縮|
|---|---:|---:|---:|
|短い文の直接読み上げ|151ms|133ms|12%|
|長い文の直接読み上げ|247ms|209ms|15%|
|世界設定あり・文字から返答|498ms|421ms|16%|
|世界設定あり・音声から返答|483ms|354ms|27%|

|条件|改善前 p95|改善後 p95|
|---|---:|---:|
|短い文の読み上げ|165ms|196ms|
|長い文の読み上げ|249ms|424ms|
|文字から返答|590ms|547ms|
|音声から返答|533ms|395ms|

中央値は改善しましたが、TTS単体のp95はこの測定では悪化しています。少数回で、GPUのクロック・共有負荷・WDDMのばらつきを含みます。すべての発話の最悪遅延が短縮したという結果ではありません。音声会話の生成完了までの中央値は666msから483msに短縮しました。

直接読み上げの文は「こんにちは。今日はいい天気ですね。」と「2027年の夏は、東日本を中心に猛暑が長引いて、墨田区の商店街で涼み番が始まったのを覚えています。」。会話の文字質問は「2027年の夏はどんな様子でしたか。あなたの体験も教えてください。」。音声入力はローカル合成した「日本の首都はどこですか」を使用しました。

生の結果は実行機の`run/performance-before.json`と`run/performance-after.json`に保存しています。これらにはテスト文章も含まれるため、Git対象外です。この表はその要約です。

## 音声の同等性と演算の比較

`compare_tts.py`は固定乱数・同じ文・スタイル強度1.8・全7表情で上流経路と比較します。FP32高速経路は全表情でサンプル数が一致し、正規化後の波形差のRMSは約0.0000018〜0.0000035でした。これは試験した文の数値的比較で、あらゆる文章の聴感を保証するものではありません。

この単体比較の中央値は上流143ms、高速FP32 130ms、高速FP16 140ms。FP16は一部の表情で音声長や波形が変わり、速くもなかったため標準採用していません。CPUスレッド1/2/4/6とTF32も比較し、CPUスレッド2・FP32を選びました。

GPU全体使用量の参考スナップショットは改善前5485MiB、改善後5630MiB。他アプリ分を含みます。未使用BERT計算・重みは減らしましたが、速度のために2スロットとCUDA領域を保持するため、全体のVRAMが最小になる構成ではありません。空きは約2.2GBありました。省メモリ優先なら`llama_slots: 1`へ変更できます。

## 何を短縮したか

- Style-Bertの未使用BERT計算と転送を省き、CUDAの一時領域を毎回捨てない。
- 会話の生成と読み上げを並行し、最初は読点でも区切って送り出す。
- Gemmaの認識・会話を別スロットへ割り当て、長い世界設定の再計算を抑える。
- HTTP接続とトークン数を再利用。WebSocket圧縮を無効化してlocalhostでの圧縮CPU負荷を省く。
- 録音ワーカーの投稿回数を約8分の1へ。終了時の端数はflushする。
- ブラウザでPCM16を直接デコード。再生予約余裕を40msから15msへ。

合成結果のキャッシュは使っていません。文脈の上限、履歴数、回答上限、モデルは維持しています。

## 体感遅延の読み方

標準の自動送信は発話後600msの無音を待ちます。短めは350ms、長めは1000msです。これに上の処理時間とブラウザ・音響機器の遅延が加わります。画面の「送信から再生予約まで」はクライアントの計測で、物理的な発音時刻ではありません。

初回起動・別の音声モデルへの切り替えは重みのロードで数十秒かかる場合があります。常駐後の数字と混同しないでください。発話中の逐次認識・自動割り込みを含む完全な全二重通話は実装していません。

## 検証と再実行

```powershell
.\.venv\Scripts\python.exe -m pytest -q
node --test tests/audio_client.test.cjs
# アプリ起動後
.\.venv\Scripts\python.exe -X utf8 scripts/benchmark.py --rounds 7
.\.venv\Scripts\python.exe -X utf8 scripts/verify_roleplay.py
.\.venv\Scripts\python.exe -X utf8 scripts/check_limits.py sbv2
# 通常のアプリを停止してから。モデルを複数ロードする比較
.\.venv\Scripts\python.exe -X utf8 scripts/compare_tts.py
.\.venv\Scripts\python.exe -X utf8 scripts/tune_tts.py
```

ロールプレイの人物・年表・差し替え、音声入力、生成中キャンセル、不正入力後の復帰、27秒入力を実モデルで確認。27秒の反復音声の返答は約4.27秒でした。認識結果には反復が残るため、ASR品質の改善を示す試験ではありません。自動送信の実マイクでの適切な無音時間は使用環境で調整してください。

モデル不要の別環境でもPython 32件、Node 3件が成功。ブラウザでは停止後の再送信、PCM再生、再生予約時間の表示を確認し、文字の挨拶から再生予約まで320msの例を記録しました。公開対象ファイルの簡易監査も通過しています。GitHub Actionsはワークフローを用意した段階で、リモート実行結果ではありません。
